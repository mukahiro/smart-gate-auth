# カード認証の技術解説

この文書は、`card/authenticator.py` で使っている技術を、ICカードに詳しくない人向けに説明する参考資料です。セットアップや起動手順は [README](README.md) を参照してください。

## 最初に全体像

学生証にはFeliCaという非接触ICカード技術が使われています。RC-S300はカードと無線通信し、USB経由でRaspberry Piへ結果を渡します。

```text
FCF学生証
   ↕ 近距離無線通信（NFC-F / FeliCa）
RC-S300
   ↕ USB・CCID
PC/SCドライバ
   ↕ pyscard
card/authenticator.py
   ↓
10桁の学籍番号
```

この実装は、カードを「所有していること」を確認するものです。PINや暗号学的な応答による本人確認は行っていません。

## NFC、FeliCa、FCFの関係

### NFC

NFCは、数cm程度の近距離で機器同士が通信する技術の総称です。交通系ICカード、電子マネー、社員証などに使われます。

### FeliCa

FeliCaはNFCで使われるカード技術の1つです。カード内には複数のシステムやサービスを持つことができ、目的の領域を指定してデータを読みます。

### FCF

FCF（FeliCa Common-use Format）は、社員証や学生証などでFeliCaを共通利用するためのデータ形式です。このリポジトリは以下の値を前提にしています。

| 項目 | 値 | 意味 |
| --- | --- | --- |
| System Code | `0xFE00` | FCFのシステムを選ぶ識別子 |
| Service Code | `0x1A8B` | FCF基本情報の領域を選ぶ識別子 |
| Block | `0` | サービス内で読み取る最初の16 bytes |
| 学籍番号 | 半角数字10桁 | このシステムが想定する個人IDの形式 |

FCFカードであっても、発行元によって個人IDの文字数や表現が異なる可能性があります。「FCFならどのカードでも10桁の学籍番号が読める」とは限りません。

## PC/SCとCCID

### PC/SC

PC/SCは、OS上のアプリがICカードリーダーを扱うための共通インターフェースです。Linuxでは主に `pcscd` がリーダーを管理し、Pythonからは `pyscard` を使ってアクセスします。

### CCID

CCIDは、USB接続のICカードリーダーで使われる機器クラスです。RC-S300固有のFeliCa操作を行うため、通常のカードコマンドだけでなくCCID Escape Commandを使います。

Escape Commandは機器固有機能への通路になるため、Linuxの `libccid` で無効化されている場合があります。その場合、`FEATURE_CCID_ESC_COMMAND` を取得できず初期化に失敗します。

## 通信処理の段階

### 1. リーダーを探す

PC/SCが認識している機器を列挙し、名前に `RC-S300` を含むリーダーを選びます。複数台ある場合は最初の1台が選ばれます。

### 2. Direct Modeで接続する

通常のカード接続ではなく、リーダー自体へコマンドを送るDirect Modeを使います。その後、Transparent Sessionを開始し、通信対象をNFC-Fへ切り替えます。

### 3. Pollingする

Pollingは、指定したSystem Codeのカードが近くにあるか問い合わせる処理です。実装は `0xFE00` を指定し、0.2秒間隔で確認します。

応答にはIDmが含まれます。IDmはFeliCaカードを通信上識別する8 bytesの値ですが、学籍番号とは別物です。この実装はIDmを利用者IDとしてAPIへ送りません。

### 4. Read Without Encryptionを送る

Pollingで得たIDm、Service Code `0x1A8B`、Block 0を指定してデータを読みます。名前の通り、これはカードと暗号学的な認証を行わずに読み取るFeliCaコマンドです。

### 5. 応答を検証する

受け取った応答について、長さ、コマンド種別、IDm、ステータス、ブロック数を確認します。その後、個人ID領域をASCII文字列として復号し、半角数字10桁であることを検査します。

## TLVとは

RC-S300から返るデータの一部はTLV形式です。TLVは次の3要素を順に並べる表現です。

- Tag: データの種類
- Length: 値の長さ
- Value: 実際の値

`find_tlv()` は応答を先頭からたどり、必要なTag `0x97` のValueを取り出します。Lengthが実データを超える場合は、壊れた応答として扱います。

## コンポーネントの責務範囲

`CardAuthenticator` が返すのは、学籍番号と認証方式 `card` を持つ `AuthenticationResult` です。次の処理は行いません。

- 入室か退出かの決定
- Smart Gate APIへの送信
- 学籍番号や入退室状態の永続化
- LCDやブザーの制御

これらは統合端末の責務です。役割を分けることで、カード通信と画面・APIの変更が互いに影響しにくくなります。

## 制約とセキュリティ

- 読み取り可能なカードを持っていれば認証できるため、紛失カードの無効化は別途必要です。
- Read Without Encryptionで取得できる領域は、リーダーに近づけられる者から読まれる可能性があります。
- 学籍番号は個人情報として扱う必要があります。
- IDmは学籍番号と同じ意味ではなく、IDmだけで人物の正当性を保証できるわけでもありません。
- 強い本人確認が必要な用途では、PIN、顔認証、管理システムによる失効確認などと組み合わせる設計を検討します。
