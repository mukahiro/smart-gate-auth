# 統合認証App 設計方針

## 1. 概要

統合認証Appは、Raspberry Pi上で顔認証、FCF学生証によるカード認証、入室・退出ボタン、LCD、圧電ブザー、Smart Gate APIへのイベント送信をまとめて制御する端末アプリケーションです。

本書は実装前の設計方針です。GPIOピン番号、LCDの型番と接続方式、ボタンの個数、ブザーの駆動回路など、実機仕様が確定していない項目は「未決定事項」にまとめます。

## 2. 基本方針

- 統合認証Appを端末操作の司令塔とする
- 入室・退出はボタンで明示的に選択する
- 顔認証とカード認証は、共通形式の認証結果を返すコンポーネントとする
- 1回のボタン操作から認証終了までを1つの認証セッションとして管理する
- 1セッションにつき入退室イベントを最大1件だけ生成する
- 認証結果から入退室イベントを生成し、Smart Gate APIへ直接送信する
- 認証App側では入退室イベントを保存せず、送信失敗時も自動再送しない
- LCDとブザーは各認証処理から直接操作せず、統合認証Appが状態に応じて制御する
- 顔画像とカメラフレームは保存しない

## 3. 顔登録サーバーの扱い

顔画像・埋め込み登録サーバーは同じリポジトリで管理しますが、統合認証Appとは別プロセスにします。

顔登録は管理系の処理であり、端末のリアルタイムな認証処理とは次の点が異なります。

- HTTPリクエストを受け付ける
- 顔画像の検証と複数回のモデル推論を行う
- 顔埋め込みDBを更新する
- 認証端末より広いネットワークアクセスを必要とする可能性がある

同一プロセスに組み込むと、モデル実行の競合、HTTP公開範囲、DB更新中の再読み込み、端末操作への影響が複雑になります。そのため、次の境界を基本とします。

| アプリケーション | 配置 | 責務 |
| --- | --- | --- |
| 統合認証App | Raspberry Pi認証端末 | 顔・カード認証、入退出選択、機器制御、API送信 |
| 顔登録サーバー | 管理サーバー、または別プロセス | 顔画像受付、埋め込み生成、登録データ更新 |

顔登録サーバーをRaspberry Pi上で動かす場合も、systemdサービスとプロセスは統合認証Appから分離します。

## 5. コンポーネント

| コンポーネント | 主な責務 |
| --- | --- |
| `TerminalApp` | 起動・終了、依存コンポーネントの管理、状態遷移の統括 |
| `SessionController` | 入退出選択から認証終了までのセッション管理 |
| `ButtonController` | 入室・退出ボタンの監視、チャタリング除去 |
| `FaceAuthenticator` | カメラ取得、顔検出、埋め込み比較 |
| `CardAuthenticator` | RC-S300の監視、FCF学籍番号の読み取り |
| `AttendanceService` | 共通入退室イベントの生成と送信制御 |
| `AttendanceApi` | Smart Gate APIとのHTTP通信 |
| `LcdController` | 状態、利用者名、エラーの表示 |
| `BuzzerController` | 成功、失敗、警告を表す鳴動パターンの再生 |

ハードウェア固有処理はインターフェースの背後に分離します。これにより、実機を接続しない開発環境ではLCD、ボタン、ブザーをテスト用実装へ置き換えられます。

## 6. 共通データ形式

### 6.1 認証結果

顔認証とカード認証は、内部的に次の共通形式を返します。

```python
@dataclass(frozen=True)
class AuthenticationResult:
    student_number: str
    method: Literal["face", "card"]
    confidence: float | None
```

- 顔認証の場合は`confidence`へコサイン類似度を設定する
- カード認証の場合は`confidence`を`None`にする
- カードのIDmはAPIへ送信せず、必要な場合だけ端末内部の診断情報として扱う

### 6.2 入退室イベント

```python
@dataclass(frozen=True)
class AttendanceEvent:
    event_id: str
    student_number: str
    device_id: str
    method: Literal["face", "card"]
    event_type: Literal["check_in", "check_out"]
    authenticated_at: str
    confidence: float | None
```

`event_type`はカードの読み取り履歴から自動的に切り替えず、ボタンの選択結果から決定します。

## 7. 操作フロー

端末負荷とプライバシーを考慮し、待機中は顔推論を行わず、入室または退出ボタンが押された後に認証受付を開始する方式を基本とします。

```text
待機
  |
  | 入室／退出ボタン
  v
認証受付
  |\
  | +-- 顔認証
  |
  +---- カード認証
  |
  | 最初の有効な認証結果を採用
  v
APIへ送信
  |\
  | +-- 成功 ------> LCD・成功音
  |
  +---- 失敗 ------> 未記録をLCD・警告音で通知
  |
  v
カード取り外し／クールダウン
  |
  v
待機
```

顔とカードがほぼ同時に認証された場合でも、セッションが最初に受理した結果だけを使用します。遅れて到着した結果は、セッションIDまたは世代番号を照合して破棄します。

## 8. 状態遷移と表示

| 状態 | LCD表示例 | ボタン・認証処理 | ブザー |
| --- | --- | --- | --- |
| `IDLE` | `入室/退出を選択` | ボタン入力を待つ | なし |
| `AUTHENTICATING` | `顔を向けるか カードをかざしてください` | 顔・カードを並行受付 | 受付音（任意） |
| `PROCESSING` | `認証しています` | 新しい認証結果を受け付けない | なし |
| `SUCCESS` | `○○さん 入室しました` | API送信完了 | 成功音 |
| `API_FAILED` | `通信エラー 記録されませんでした` | イベントを保存せず待機へ戻る | 警告音 |
| `AUTH_FAILED` | `認証できませんでした` | タイムアウト後に待機へ戻る | 失敗音 |
| `DEVICE_ERROR` | `端末エラー 管理者に連絡` | 復旧可能な機器だけ再初期化 | 異常音 |
| `COOLDOWN` | `カードを離してください` | 重複認証を抑止 | なし |

状態表示が短時間で上書きされないよう、成功・失敗メッセージには最低表示時間を設けます。ただし終了処理や重大エラーは待たずに割り込み可能とします。

## 9. 並行処理

統合認証Appの中心にはイベントキューを置き、顔認証、カード認証、GPIO入力からの通知を1か所で直列に処理します。

- 顔推論はモデルを起動時に1回だけ読み込み、専用ワーカーで実行する
- RC-S300のポーリングは専用ワーカーで実行する
- GPIOコールバックでは重い処理を行わず、ボタンイベントだけをキューへ入れる
- LCDへの書き込みとブザー制御は同時実行せず、それぞれのコントローラーで直列化する
- API通信はカメラやカードの監視を停止させない
- 終了時は新規セッションを停止し、カメラ、カード、GPIO、LCD、DB、HTTPセッションを順番に解放する

単純な`asyncio`化だけでは、InsightFaceやPC/SCの同期処理がイベントループを停止させる可能性があります。同期的な機器処理と推論はワーカースレッドへ分離し、統合部分だけでイベントキューを扱う構成を想定します。

## 10. API送信

認証成功後に入退室イベントをメモリ上で生成し、`POST /api/v1/attendance-events`へ直接送信します。認証App側に入退室イベント用のSQLite、ファイル、送信キューは持ちません。イベントオブジェクトは、その送信処理が終わった時点で破棄します。

APIから成功応答を受け取った場合だけ、LCDとブザーで記録成功を通知します。タイムアウト、接続エラー、HTTPエラーの場合はイベントを保存せず、自動再送もしません。「記録されませんでした。もう一度操作してください」など、利用者が再操作の必要性を判断できる表示と警告音を出します。

各認証操作では一意な`eventId`を生成します。APIが応答を返す前に接続が切れた場合、サーバー側では記録済みか判定できない可能性があります。利用者が再操作すると別の`eventId`が生成されるため、この曖昧性や重複の扱いはAPI側の入退室整合性チェックで対応します。

現在のカード認証Appに含まれる`EventStore`、`card_status`、`pending_attendance_events`、未送信イベントの再送処理は、統合時には使用しません。FCF読み取りとAPIクライアントを分離して再利用し、`eventType`はボタンの選択結果から設定します。

## 11. 顔埋め込みDBの更新

現在の顔認証Appは起動時に顔埋め込みを読み込むため、顔登録サーバーがDBを更新しても実行中の認証データには反映されません。統合時には次のいずれかが必要です。

1. バージョン付きDBスナップショットを端末へ配布し、検証後に原子的に切り替える
2. 同一端末上の登録サーバーから更新通知を受け、認証セッション外で再読み込みする
3. DBの更新時刻を定期確認し、変更時に再読み込みする

推奨は、管理サーバーから署名またはハッシュ付きのバージョン済みスナップショットを配布し、端末側で検証してから切り替える方式です。更新に失敗した場合は、直前の正常なデータを使い続けます。

モデル名と埋め込みの次元もDBのメタデータとして保存し、端末の認証モデルと一致しない登録データを拒否できるようにします。

## 12. LCD制御

LCD表示は次の優先順位で扱います。

1. 終了不能なハードウェアエラー
2. API送信結果と認証結果
3. 認証受付中の案内
4. 通常の待機表示

APIが返す`lcdDisplayName`を成功画面に使用します。通信障害時は成功画面を表示せず、「記録されませんでした。もう一度操作してください」のような共通メッセージを表示します。

LCDの文字数、文字コード、カタカナ変換、改行位置は使用機種に合わせて表示アダプター内で処理します。

## 13. 圧電ブザー制御

音の意味が重ならないよう、短く区別しやすいパターンにします。

| 結果 | パターン案 |
| --- | --- |
| ボタン受付 | 短音1回 |
| 認証・記録成功 | 高めの短音2回 |
| 認証失敗 | 低めの短音2回 |
| API送信失敗 | 長音1回 |
| 機器異常 | 低音3回 |

能動ブザーはON/OFFのみ、受動ブザーはPWMによる周波数制御が必要です。実装方式は採用するブザーの種類と駆動回路が決まってから確定します。

## 14. 障害時の動作

| 障害 | 基本動作 |
| --- | --- |
| API停止・ネットワーク断 | 保存・再送せず、未記録であることを通知して端末動作を継続 |
| カメラ異常 | カード認証を継続し、LCDへ縮退状態を表示 |
| RC-S300異常 | 顔認証を継続し、カードリーダーの再初期化を試行 |
| LCD異常 | ログとブザーで通知し、認証処理は可能なら継続 |
| ブザー異常 | LCDとログで通知し、認証処理を継続 |
| 顔DB異常 | 顔認証を停止し、カード認証だけで継続 |

カード認証と顔認証の一方だけが故障した場合に端末全体を停止させない、縮退運転を基本とします。

## 15. セキュリティとプライバシー

- カメラは認証セッション中だけ使用する
- カメラフレームや登録元画像を保存しない
- 顔埋め込みDBを必要なプロセスだけが読める権限にする
- API tokenやDBをGitへコミットしない
- 顔登録APIをインターネットへ直接公開しない
- LCDへ学籍番号や内部エラーを必要以上に表示しない
- ログへ顔埋め込み、画像、Bearer tokenを出力しない
- 写真によるなりすまし対策が必要な場合は、ライブネス検知または追加認証を検討する

## 17. 実装順序

1. 共通の`AuthenticationResult`と`AttendanceEvent`を定義する
2. カード認証AppからFCF読み取りとAPI通信を分離し、イベント保存処理を除外する
3. API送信処理を顔・カード共通にする
4. ボタン入力と認証セッションの状態機械を実装する
5. カード認証を統合認証Appへ接続する
6. 顔認証をモデル常駐型コンポーネントへ変更して接続する
7. LCDを状態遷移へ接続する
8. 圧電ブザーの通知パターンを接続する
9. 顔DBの更新・再読み込み方式を実装する
10. systemdによる自動起動、再起動、ログ管理を設定する
11. 実機で競合、連続操作、通信断、機器切断を試験する

## 18. 実機試験項目

- 入室・退出の各ボタンが正しい`eventType`になる
- ボタンのチャタリングで複数セッションが開始されない
- 顔とカードが同時に成功してもイベントが1件だけ作成される
- カードを置いたままにしても重複認証されない
- 認証タイムアウト後にカメラが解放される
- API停止・通信断時にイベントが端末へ保存されない
- API送信失敗時に、未記録であることと再操作の必要性が表示される
- 顔DB更新中に認証処理が不整合なデータを読まない
- カメラ故障時にカード認証だけで継続できる
- カードリーダー故障時に顔認証だけで継続できる
- LCDとブザーの通知が実際の処理結果と一致する
- 終了時やsystemd停止時にGPIO、カメラ、RC-S300を解放できる

## 19. 未決定事項

実装前に次の仕様を確定する必要があります。

- 入室・退出ボタンの個数とGPIOピン番号
- プルアップ／プルダウン方式とチャタリング除去時間
- ボタン操作後の認証タイムアウト時間
- LCDの型番、接続方式、表示桁数、文字コード
- 圧電ブザーが能動型か受動型か
- ブザーのGPIOピン、駆動電圧、トランジスタ回路の有無
- 顔とカードが同時に異なる人物を返した場合の運用ルール
- 顔登録サーバーと認証端末間の顔DB配布方式
- オフライン時も利用者名をLCD表示するためのローカルキャッシュ要否
- 認証受付中のキャンセル操作
- 同一人物の連続入室・連続退出を許可するか、API側で警告するか

## 20. 回路設計
- Pi 5 Pin 1   3.3V   → LCD VCC
- Pi 5 Pin 3   GPIO2  → LCD SDA
- Pi 5 Pin 5   GPIO3  → LCD SCL
- Pi 5 Pin 6   GND    → LCD GND / ボタンGND / ブザーGND
- Pi 5 Pin 11  GPIO17 → 入室ボタン
- Pi 5 Pin 13  GPIO27 → 退出ボタン
- Pi 5 Pin 12  GPIO18 → ブザー

採用ブザー `PKM13EPYH4000-A0` は発振回路を内蔵しない圧電サウンダーです。GPIO18を単純にON/OFFするのではなく、共振周波数に合わせた4 kHz、デューティ比50%のPWMで駆動します。周波数は起動オプション `--buzzer-frequency` で変更できます。定格欄の30 Vp-pは最大許容値であり、30 Vを印加する指定ではありません。

## 21. 実装と起動

統合認証Appは `python -m terminal.app` で起動します。次の環境変数を設定してください。

```bash
export AUTH_APP_BEARER_TOKEN='replace-with-a-long-random-secret'
export AUTH_API_BASE_URL='http://localhost:3000'
export AUTH_DEVICE_ID='smart-gate-terminal-01'
export FACE_AUTH_DB_PATH='face/face.db'
python -m terminal.app
```

開発PCでは、GPIOボタンとブザーをコンソールへ置き換えられます。

```bash
python -m terminal.app --console-buttons --console-hardware
```

顔またはカードの初期化に失敗した場合は、正常な認証方式だけで縮退運転します。両方が利用できない場合は起動を中止します。LCDは型番と文字コードが未決定のため、現在は `ConsoleLcd` を使用しています。実機LCDのアダプターは `terminal/hardware/lcd.py` の `Display` インターフェースとして追加してください。

systemdの雛形は `terminal/smart-gate-terminal.service` にあります。配置先、実行ユーザー、GPIO・カメラ・PC/SCへのアクセス権を実機に合わせて調整してから使用してください。

ハードウェアを使わない単体テストは次のコマンドで実行します。

```bash
python -m unittest discover -s terminal/tests -v
```
