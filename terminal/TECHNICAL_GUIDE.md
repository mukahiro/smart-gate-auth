# 統合認証端末の技術解説

この文書は、`terminal/` が顔認証、カード認証、ボタン、LCD、ブザー、HTTP APIをどのように統合しているかを、組み込み開発や非同期処理に詳しくない人向けに説明する参考資料です。設置、起動、操作の手順は [README](README.md) を参照してください。

## 「統合」するソフトウェア

顔認証とカード認証は、利用者を特定する方法が異なります。しかし、特定後に必要な処理は共通です。

- 入室か退出かを決める
- 認証結果を共通形式へする
- イベントをAPIへ送る
- LCDとブザーで結果を通知する
- 次の利用者を受け付けられる状態へ戻す

`terminal/` はこれらを制御する中心です。顔やカードの認証処理自体は別コンポーネントに分け、端末は共通の認証結果だけを受け取ります。

## コンポーネント構成

| コンポーネント | 役割 |
| --- | --- |
| `TerminalApp` | 設定の読み込み、機器初期化、起動と終了 |
| `SessionController` | 1回のボタン操作から結果表示までの進行管理 |
| `FaceAuthenticator` | カメラで顔を照合し、学籍番号と類似度を返す |
| `CardAuthenticator` | RC-S300から学籍番号を読み取る |
| `AttendanceClient` | 入退室イベントをHTTPでAPIへ送る |
| `ButtonController` | GPIOボタンの入力を入室・退出に変換する |
| `I2cLcd` / `ResilientDisplay` | LCD表示と、故障時のログ出力への切り替え |
| `GpioBuzzer` | 状態に応じた音のパターンを再生する |

この分割により、例えばLCDが変更されても、顔照合やAPIペイロードの実装を直接変更せずに済みます。

## 共通の認証結果

顔とカードは、最終的に `AuthenticationResult` という同じ形のデータを返します。

```text
AuthenticationResult
├─ student_number : 半角数字10桁
├─ method         : face または card
└─ confidence     : 顔認証のときだけ必要
```

この共通形式があるため、その後のイベント生成とAPI送信は認証方式によらず同じ処理で行えます。カード認証に類似度はないため、`confidence` を付けることはできません。

## 状態機械

端末は「今どの段階にいるか」を `TerminalState` で管理します。処理の段階を明確にする設計を状態機械と呼びます。

```text
IDLE
  → AUTHENTICATING
      ├─ 認証なし → AUTH_FAILED → IDLE
      ├─ 機器障害   → DEVICE_ERROR → IDLE
      └─ 認証成功 → PROCESSING
                         ├─ API成功 → SUCCESS
                         └─ API失敗 → API_FAILED
                                      → COOLDOWN
                                      → IDLE
```

状態に合わせてLCD表示とブザー音を変えることで、処理中に次の操作を受け付けたり、通信失敗を認証失敗と表示したりする混乱を防ぎます。

## 非同期処理とスレッド

Raspberry Pi上では、次のように完了まで時間のかかる処理が複数あります。

- カメラ画像の取得と顔推論
- ICカードがかざされるまでの待機
- HTTPレスポンスの待機
- LCDへのI2C通信
- ブザーのメロディ再生

これらをすべて1本の順番処理にすると、一方の完了を待つ間に他方を処理できません。そこで、端末全体の進行にPythonの `asyncio`、同期的な機器操作に `ThreadPoolExecutor` を使います。

`asyncio` は、待ち時間に別の仕事を進めるための制御を担当します。スレッドプールは、カメラやカードのような同期APIをメインの非同期処理から切り離します。

## 顔とカードの競争

認証開始時に、顔とカードの `authenticate()` を並行して実行します。最初に有効な結果を返した方式が採用されます。

```text
顔認証   ────┐
                 ├──→ 最初の成功結果を1件だけ採用
カード認証 ────┘
```

結果が決まるとキャンセル用イベントを設定し、もう一方の処理に停止を依頼します。ワーカーはそのイベントを定期的に確認し、協調的に終了します。強制終了ではないため、機器リソースの後始末を実行できます。

## GPIOボタン

GPIOはRaspberry Piで電気信号を入出力するピンです。入室と退出のボタンは、内部プルアップ抵抗を使うアクティブLow構成です。

- 押していないとき: 入力はHigh
- ボタンを押してGPIOとGNDがつながったとき: 入力はLow
- HighからLowへ変わる立ち下がりをボタン操作として検出

物理的なボタンは1回押しても接点が短時間に何度か振動することがあります。これをチャタリングと呼びます。実装はGPIOライブラリの `bouncetime` と、前回操作時刻との比較の両方で連続入力を除外します。

## I2CとLCD

I2Cは、2本の信号線を使って複数の機器と通信できるバス方式です。

- SDA: データ線
- SCL: クロック線
- Address: 同じバス上で機器を区別する番号

LCD2004は本来多くの信号線を必要としますが、PCF8574バックパックがI2CのデータをLCD用信号へ変換します。実装は1 byteを4 bitずつ送り、Enable信号をパルスさせてLCDへ取り込ませます。

LCDの文字ROMが扱える範囲に合わせ、ASCII文字と半角カタカナを表示します。表示幅の20文字を超える行は、別スレッドが一定間隔で表示位置をずらしてスクロールします。

`ResilientDisplay` はI2Cエラーが発生するとLCDを故障状態とし、以後の表示をログへ切り替えます。LCDの故障で認証とAPI送信まで停止しないための設計です。

## PWMとブザー

パッシブブザーは、一定の周波数で電圧をON/OFFすると音が出ます。PWM（Pulse Width Modulation）は、GPIOのON/OFFを高速に繰り返す方法です。

実装は基準周波数を4000 Hzとし、その比率と鳴動時間を組み合わせて次の状態を区別します。

- 認証受付
- 認証とAPI記録の成功
- 認証失敗
- API通信失敗
- 認証機器の障害

音の違いは利用者へ状態を伝える補助であり、LCD表示や運用上の確認を完全に代替するものではありません。

## HTTP APIと入退室イベント

認証成功後、`AttendanceEvent` が次の情報をまとめます。

| 項目 | 意味 |
| --- | --- |
| `eventId` | イベントごとに生成するUUID |
| `studentNumber` | 半角数字10桁の学籍番号 |
| `deviceId` | どの端末から送ったかを表すID |
| `method` | `face` または `card` |
| `eventType` | `check_in` または `check_out` |
| `authenticatedAt` | タイムゾーンを含むISO 8601形式の日時 |
| `confidence` | 顔認証の類似度。カードでは送らない |

`AttendanceClient` はBearer tokenを `Authorization` ヘッダーに付け、JSONとしてPOSTします。API側の応答に次の条件を求めます。

- HTTP statusが200または201
- JSON objectである
- 応答の `eventId` が送信した値と一致する
- `status` が `recorded` または `duplicate`

`eventId` はAPI側が同じイベントの二重登録を判定するための識別子です。ただし、現在の端末はイベントを永続化しないため、送信失敗後に同じ `eventId` を自動再送することはありません。

## 障害時の考え方

端末は、一部の故障がすべての機能を停止させないように、いくつかの縮退動作を持ちます。

| 障害 | 動作 |
| --- | --- |
| 顔認証の初期化失敗 | カード認証だけで起動 |
| カード認証の初期化失敗 | 顔認証だけで起動 |
| 顔とカードの両方が初期化失敗 | 利用できる認証手段がないため起動中止 |
| LCDの初朖化失敗 | ログ表示で続行 |
| LCDの実行中エラー | 以後はログ表示で続行 |
| ブザーの初期化失敗 | 音の代わりにログを出力 |
| API送信失敗 | 未記録として表示し、自動再送しない |

これは「必ず動き続ける」ことだけを目的としたものではありません。認証結果をAPIへ記録できない場合は成功と表示せず、ユーザーに再操作を求めます。

## systemdの役割

systemdはLinuxのサービス管理機構です。`smart-gate-terminal.service` により、次の運用が可能になります。

- OS起動時に端末アプリを自動起動する
- 異常終了時に自動再起動する
- 環境変数を別ファイルから読む
- `journalctl` でログを一元管理する
- 専用ユーザーの権限で実行する

サービス化は自動的に安全性を保証するものではありません。実行ユーザーにはGPIO、I2C、カメラ、PC/SCを使うのに必要な範囲だけ権限を与える必要があります。

## 設計上の制約

- イベントのローカルキューや自動再送はありません。
- ボタン操作をしない限り、顔やカードの認証セッションは始まりません。
- 認証セッション中の追加ボタン入力は、次のセッション用に保留されず無視されます。
- 認証の成功と入退室記録の成功は別です。APIの正常応答を確認して初めて成功表示になります。
- 現在の顔認証にライブネス検知はありません。
- カード認証はRead Without Encryptionで学籍番号を読む方式です。
